## 0. 现状一句话

- 后端**确定性引擎已跑通 S1—S4 + 终局**：`scripts/run_hefei_first_barrage.py`（硬编码动作冒烟）。
- **S1 完整交互闭环已跑通**：`scripts/run_s1_agent_loop.py`（预览 → 选方案 → 企业协商 → 结算）。
- **前端（React/Convex）尚未接入 Python 引擎**，引擎目前通过 CLI 写 JSON 文件输出。

所以「最小闭环」的缺口不是算法，而是**把引擎的确定性循环接成前端可操作的端到端流程**，并把 S1 已验证的交互推广到 S2—S4。

---

## 1. 端到端流程（状态机视角）

```text
new_run(run_id, company_ids, seed)
        │  → SimulationState（城市指标 + 2~3 家企业初始状态）
        ▼
┌─────────────────────────────────────────────┐
│  对每个阶段 S1 → S2 → S3 → S4 重复：          │
│                                             │
│  ① 进入阶段：展示 Context + 财政池 + 企业申请   │
│  ② 四部门初审 → 质询 → 联席方案（deliberation） │
│  ③ 玩家选方案 + 提交条件单                     │
│  ④ 企业回应 / 反提案                          │
│  ⑤ run_stage(actions, negotiations) 结算     │
│     → StageResult（deltas + budget + 新状态） │
│     → next_state 进入下一阶段                 │
└─────────────────────────────────────────────┘
        │
        ▼
finalize(state) → FinalResult（组合结果 + Historical Replay + 分叉点）
```

关键点：**整个循环是确定性的**。`run_stage` 一次调用 = 完整跑完一个阶段并返回 `next_state`；「预览」和「结算」用同一输入可复现（当前 `deliberate` 为 deterministic fallback），因此前端可以先拿预览、玩家决策后再结算，两次结果一致。

## 2. 引擎接口清单（前端唯一依赖）

| 方法 | 输入 | 输出 | 前端用途 |
|---|---|---|---|
| `InvestmentEngine.new_run` | `run_id`, `company_ids[]`, `seed` | `SimulationState` | 开局 |

## 3. 前端操作细节（每个阶段的 7 步）

> 下表「数据来源」字段均指 `StageResult` / `SimulationState` / `DeliberationRound` 内的路径，前端按 `model_dump(mode="json")` 后的 JSON 键读取。

| # | 页面 | 用户操作 | 数据来源（接口 / 字段） | 展示要点 |
|---|---|---|---|---|
| ① 进入阶段 | 决策驾驶舱 | 无（自动） | `SimulationState.city_metrics`、`treasury_balance`；`BudgetState.new_fiscal_capacity`、`assumption` | 城市 8 指标、本轮财政池（可用点数 = 结转 + 新增）、阶段事件卡（`event.description`）、cutoff 日期 |
| ② 读申请 | 企业申请卡 | 浏览 | `CompanyState`（display_name 匿名、archetype、capital_request、financial_health、technology_readiness、capital_intensity、construction_progress） | 多家同时呈现，突出机会成本；**不显示真实案例名和 cutoff 后结果** |
| ③ 部门研判 | 联席研判页 | 展开/折叠 | `DeliberationRound.department_memos`（4 部门：recommendation / core_claim / red_lines / confidence）；`meeting.consensus` / `unresolved_disagreements` / `critical_question` / `challenges` | 默认折叠，只显示联席摘要；可展开看四部门立场、质询（`challenges` 的 from→to / stance_before→after） |
| ④ 关键核验 | 协商页 | 选一张问题卡 | `verification_question`（critical_proposition / question）；`enterprise_disclosure`（response_type：disclose/range/refuse/exchange_condition） | 展示企业披露结果，突出「关键未穿透项」是否被穿透 |
| ⑤ 选方案 | 方案卡 | 从 ≥2 个 `proposals` 中选一个 | `meeting.proposals[]`（label / recommendation / capital_points / support_focus / tranches / conditions / exit_condition） | 每个方案带出资点数、分期、条件、少数意见；玩家选择 = 生成 `PlayerAction` + `NegiationChoice` |
| ⑥ 企业回应 | 协商页 | 接受 / 接受反提案 / 拒绝 | `enterprise_response`（response_type / agreed_capital_points / rationale）；`enterprise_counteroffer`（requested_changes） | 一次反提案；玩家确认后把 `actions` + `negotiations` 打包送结算 |
| ⑦ 结算 | 阶段结算页 | 无（自动） | `StageResult.budget`（before/spent/after）、`state_deltas[]`（before/delta/after/reason_code/evidence_ids）、`company_actions[]`、`companies[]` 新状态、`events[]` | 财政条变化 + 企业状态变化 + 因果链（每条 delta 可点开看 evidence） |

之后用 `StageResult.next_state` 进入下一阶段，重复 ①—⑦；四阶段完成后调 `finalize`。

## 4. 信息截止展示（贯穿全程）

这是产品最有辨识度的点，前端必须能展示「当时可知 / 当时不可知」：

- `StageResult.frozen_context_audit`：
  - `visible_evidence_ids` → 本轮可进研判的证据；
  - `decisions[]` → 每条证据的 `decision`（visible/withheld）+ `reason_code`（`published_after_cutoff` / `withheld_outcome` 等）。
- 前端两种模式：
  - **玩家模式**：被过滤的只显示「当时不可知」，**不泄露具体未来结果**；
  - **审计模式**：显示完整原因，如「2011-06-30 才公开，晚于 S1 截止日 2008-09-30」。

证据抽屉每条至少展示：所属期、最早可知日、本轮截止日、能否进入、来源类型、质量等级、原 URL、归档状态。

## 5. 终局对照页操作细节

`finalize(state)` 返回 `FinalResult`，前端展示三块：

1. **组合结果**：`portfolio_result`（active_companies / average_construction_progress / average_financial_health / portfolio_public_value）。
2. **历史回放评分**：`historical_replay`（direction_score / sequence_score / mechanism_score / path_feedback_score / leakage_audit_passed + `score_basis` 解释）。
3. **分叉点**：`branch_points[]` + `replay_evidence`（`FrozenContextAudit`，终局解锁 withheld 结果）。

终局**揭示企业真实原型**：把 `CompanyState.archetype` / `historical_case_id` 映射回真实案例名（见第 2 节表），并并列展示「用户世界线 vs 真实历史关键决策 vs 真实结果」。

## 6. 关键决策点：前端如何接 Python 引擎（待拍板）

当前引擎只在 CLI 输出 JSON，前端是 React/Convex。三条路：

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| A. 轻量 HTTP 层（推荐） | Python 起一个只读 HTTP 服务，暴露 `new_run` / `run_stage` / `finalize` 三个端点，返回契约 JSON；前端 fetch | 新增一个 `server.py`，不动引擎 | 真闭环、真交互，改动小 |
| B. CLI 预生成静态 JSON | 先跑 `investment-run` 生成 `demo_run.json`，前端读静态文件 | 无交互，只能演示 | 抢时间、评委只演示 |
| C. 引擎移植到 Convex(TS) | 把规则引擎重写进前端后端 | 工作量大、易漂移 | 不推荐 |

推荐 A：它守住「确定性规则引擎在 Python、前端只消费结构化结果」的边界，且三方可按契约并行开发（后端冻结 HTTP 契约 = pydantic 契约的 JSON 序列化，前端按第 3 节写页面，互不等）。
