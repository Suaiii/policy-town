# 合肥产业投资推演系统：MVP 收敛与 10 小时开发方案

## 0. 文档定位

- 文档类型：实施说明（Explanation + How-to）
- 面向对象：10 小时极限开发中的产品/全栈主体、前端、Agent 架构三位成员
- 用户目标：把现有项目收敛成一个能够被演示、被历史反证、能够继续扩展的单人政府产业投资推演沙盘
- 本轮范围：单人游玩、2007—2016 历史阶段、六个企业原型、财政点数分配、Context、Agent 推演、Historical Replay、三人开发分工
- 本轮不做：精确宏观经济预测、多人协作、开放世界、自由文本政策解析、运行时抓取全网、多模态材料解析

---

## 1. 一句话产品定义

> 玩家扮演 2007—2016 年间的合肥产业投资决策者。系统从六个真实企业原型中选出 2—3 家进入同一局，在相同城市 Context 和外部事件下竞争有限财政点数；玩家完成投资、配套、追加或退出决策后，所有入局企业继续演化，系统再用被隐藏的真实历史路径检验推演是否站得住。

这条主线只有一个核心循环：

```text
历史阶段与当期 Context
        ↓
从六个原型中选择 2—3 家并载入完整背景
        ↓
企业同时提出资金需求，玩家分配有限财政点数
        ↓
四个 Agent 判断企业、产业、市场与财政约束
        ↓
每家企业根据投入、背景和事件自主行动
        ↓
规则引擎结算企业与政府共同的 Next State
        ↓
结果反哺城市与下一阶段，再与真实历史路径对照
```

产品卖点不是“把真实成功案例写成必胜脚本”，而是：

> 核心差异化卖点：截止日冻结推演。系统不把完整历史答案交给 Agent，而是按照材料最早公开时间冻结每一阶段的可见信息；后来财报、评级报告与真实结果只在终局 Replay 解锁，使历史推演成为可审计的盲测，而不是后见之明复述。

1. 同一笔政府决策会同时改变企业、财政、产业链与下一轮机会；
2. 同一局内 2—3 家企业必须争夺同一份钱，给一家追加就意味着放弃另一家；
3. 六个企业原型全部经过同一套状态转移，而不是成功/失败两套脚本；
4. 历史上的成功企业在错误投入、错过窗口或过早退出时也可以失败；
5. 当玩家复现当时合肥的关键决策序列时，系统应在容差内复现相应历史方向和里程碑，这是推演引擎必须通过的校准基线。

## 2. 角色与企业原型

### 2.1 玩家角色

玩家控制的是“合肥产业投资决策者”，不是某一家企业。企业由系统 Agent 运行，玩家决定政府是否投入、投入多少、用什么方式投入以及何时退出。

### 2.2 六个企业原型

第一版沿用六个真实案例作为后台原型，但前台可以匿名化。六个原型都必须具备可运行的初始状态、资金需求、企业决策逻辑、事件敏感性、状态转移和历史校准目标。表中的“主要检验”只是说明该案例最适合检验哪种机制，不是给企业预先贴上成功或失败标签。

| 原型 | 后台历史案例 | 主要检验 | MVP 结果维度 |
|---|---|---|---|
| A 大型显示制造 | 京东方合肥项目 | 逆周期投资与本地产业基础 | 产能爬坡、市场承压、家电协同 |
| B 半导体存储 | 长鑫存储 | 长周期资本与持续研发 | 研发里程碑、追加压力、产业链形成 |
| C 高端装备技术 | 鑫昊等离子 | 技术路线和商业化能力 | 技术可行、订单转化、规模化困难 |
| D 光伏制造 | 赛维 LDK | 高景气扩产与周期反转 | 价格冲击、负债压力、产能过剩 |
| E 重型装备 | 熔安/熔盛 | 本地产业匹配和重资产风险 | 需求波动、资产沉淀、退出损失 |
| F 生物医药 | 北大未名 | 企业执行与治理能力 | 建设兑现、管理风险、项目停滞 |

### 2.3 六个原型如何进入同一局

六个原型不是六个独立关卡。开局先按照所选历史阶段，从六个原型中选择 2—3 家在该时点合理存在的企业，向它们分别提供完整的截止日前背景。三家企业同时向政府提出资金需求，玩家不能逐家无成本地试答案，而要在同一个财政池中做取舍。

入局之后，这 2—3 家企业都持续运行：

```text
企业初始状态
+ 获得的财政点数与支持工具
+ 企业自己的经营/研发/融资动作
+ 同期产品、政策与历史事件
+ 从城市获得的产业链和人才协同
        ↓
下一阶段企业状态
```

没有获得投资的企业也不能被冻结。它可以缩减项目、寻找外部融资、迁往其他城市、错过建设窗口或在后续再次提出申请。已经获得投资的企业也不会被标记为成功；资金不足、支持结构错误、后续断投、市场反转或企业执行失败，都可能让它走向停滞甚至退出。

### 2.4 历史校准是引擎基线，不是剧情锁定

每个原型都保存一条后台“历史决策轨迹”和一条“真实结果轨迹”。它们只在校准和终局对照时使用，不直接发送给运行中的企业 Agent。

必须满足的核心验收是：

> 当系统载入真实时点 Context、真实外部事件，并输入当年合肥在投资规模、持续追加、基础设施和产业链支持方面的关键决策时，企业状态应在允许容差内走向真实历史方向；改变关键决策后，企业可以长出不同结果。

因此，“按照历史决策应当成功”指的是模型校准要求，而不是在代码中写一条 `historical_action => success`。如果一条历史轨迹只能靠结果硬编码复现，它不能证明推演有效。

### 2.5 所谓“自由生长”的工程含义

“自由生长”不是让 LLM 随意编数字，而是让企业 Agent 在真实背景与当前状态下自由选择结构化动作，再由统一规则结算结果：

```text
企业 Agent 可选动作：扩建 / 研发 / 融资 / 获取订单 / 收缩 / 迁移 / 等待
政府玩家可选动作：投资 / 配套 / 追加 / 重组 / 退出
事件系统：改变需求、价格、融资、供应链、政策和建设条件
规则引擎：更新现金、债务、建设、技术、产能、订单和城市资产
```

这样，六个原型共享同一套“生长语法”，差异来自它们的真实初始 Context、资金结构、技术路线、市场暴露和执行能力。

## 3. 回合与 Context 流程

### 3.1 MVP 采用四阶段，而不是逐年十回合

10 小时版本建议把 2007—2016 压缩为四个“决策窗口”。每个窗口代表一段历史时期，既保留路径依赖，也能在 5—8 分钟内演示完整闭环。

| 阶段 | 建议历史窗口 | 玩家看到的核心矛盾 | 主要操作 |
|---|---|---|---|
| S1 产业底座 | 2007—2008 | 财政能力有限，但逆周期项目出现 | 首投与配套 |
| S2 扩产抉择 | 2009—2011 | 早期项目需要追加，新项目同时出现 | 追加、引链、拒绝 |
| S3 周期分化 | 2012—2014 | 有的行业下行，有的技术窗口形成 | 止损、重组、继续投入 |
| S4 长期下注 | 2015—2016 | 短期财政回报与长期战略能力冲突 | 组合再平衡、长期投资 |

未来若需要更高精度，可以把每个阶段拆为年度回合，数据契约无需改变。

### 3.2 一轮 Context 的生成顺序

```text
① 载入上一轮 State
② 应用本轮已发生且在截止日前可知的外部事件
③ 从六个可运行原型中选择 2—3 家并载入各自初始状态与资金请求
④ 拼装 City + Industry + Company + Project Context
⑤ 删除未来结果、企业名称和截止日后信息
⑥ 映射为 0—100 可读量表，并保留后台原始值与来源
⑦ 2—3 家企业同时提出资金需求，玩家分配财政点数及支持工具
⑧ 专业 Agent 给出判断，企业 Agent 分别选择下一步经营动作
⑨ 规则引擎对所有入局企业同时结算 Next State
⑩ 未投资企业也继续变化，所有结果共同更新城市与下一轮 Context
```

这里的“匿名化”仅仅用于防止玩家靠记忆直接选择答案；底层数据仍然对应真实案例和真实时点。

### 3.3 信息分层

前台不能把几十个字段一次性扔给玩家。采用三层信息展示：

- 首屏 8 项：财政余量、产业基础、市场景气、企业财务、技术成熟、项目资本强度、执行能力、政策窗口；
- 展开卡片：展示支撑 8 项判断的 12—16 个原始或派生指标；
- 证据抽屉：展示来源、发布日期、有效期、质量等级和缺失说明。

## 4. 指标筛选：保留什么，删除什么

### 4.1 筛选门槛

一个指标只有同时通过以下四关，才能进入 MVP：

1. 可获得：至少有一种稳定的官方、上市公司或权威行业来源；
2. 有时点：能判断该信息在模拟截止日是否已经公开；
3. 可结算：玩家动作或外部事件能通过清楚规则影响它，或者它能影响结果；
4. 可解释：评委能在 30 秒内理解它为什么影响决策。

若指标没有连续实数，但有可靠的分档事实，可以使用 A/B/C 或 0—100 的证据分档；必须保存 `value_type` 与 `confidence`，不能把估计值伪装成官方实数。

### 4.2 MVP 最小指标集

以下 18 个状态指标足以支撑第一版推演。`★` 为前台首屏指标，其他进入详情或由规则引擎使用。

| 层级 | 指标 | 作用 | 主要可行来源 | MVP 处理 |
|---|---|---|---|---|
| 城市/政府 | `fiscal_budget` ★ | 上期结转与场景新增额度共同形成的可分配财政点数 | 合肥预算执行报告、财政决算、项目与基金资料 | 当前为显式 `scenario_assumption`；滚动结转，数据补齐后按 replacement key 替换 |
| 城市/政府 | `committed_capital` | 已投项目锁定的资金 | 历史项目投资与玩家决策 | 规则累计 |
| 城市/政府 | `industrial_base` ★ | 本地是否有客户、制造与配套 | 统计公报、工业产值、产品产量 | 产业分项 0—100 |
| 城市/政府 | `talent_supply` | 人才和科研承载 | 年鉴、高校/科研机构公开数据 | 0—100 |
| 城市/政府 | `infrastructure_capacity` | 土地、能源、园区承载 | 规划/政府公开资料 | 0—100 |
| 产业/市场 | `market_cycle` ★ | 当前景气和需求方向 | 行业协会、权威价格/产量资料 | -100—100 方向量表 |
| 产业/市场 | `product_price_trend` | 价格上行或下行 | 行业资料、企业年报 | 同比或方向档位 |
| 产业/市场 | `supply_pressure` | 产能扩张和竞争压力 | 行业产能/产量/厂商资料 | 0—100 |
| 产业/市场 | `policy_support` ★ | 国家政策窗口 | 国务院、部委正式文件 | 0—100，按有效期 |
| 企业 | `financial_health` ★ | 企业能否持续投入 | 年报/审计报告：现金、负债、经营现金流 | 组合分数 + 原字段 |
| 企业 | `execution_ability` ★ | 历史建设、管理和融资兑现 | 年报、项目时间线、公开事实 | 证据分档 |
| 企业 | `technology_readiness` ★ | 技术是否接近商业化 | 专利不是唯一代理；以量产/认证/良率证据为主 | 0—100 + 置信度 |
| 企业 | `customer_order_strength` | 客户与订单是否支撑产能 | 年报、公告、可信报道 | 0—100 或缺失 |
| 项目 | `capital_intensity` ★ | 项目对财政的挤占 | 总投资、政府出资、建设期 | 点数成本 |
| 项目 | `construction_progress` | 项目是否按期形成资产 | 项目时间线 | 0—100 |
| 项目 | `production_ramp` | 产能、良率和商业化进度 | 公告/年报/官方项目资料 | 0—100 |
| 项目 | `project_cashflow` | 是否需要追加、是否可退出 | 财务/项目公开数据 + 规则 | -100—100 |
| 政府结果 | `portfolio_public_value` | 税收、就业、产业链与股权价值的综合反馈 | 上述状态的规则结算 | 仅做结果面板，不作为原始事实 |

### 4.3 第一版应剔除或降级的指标

| 指标 | 处理 | 原因 |
|---|---|---|
| 政府债务精确值 | 降级为财政压力档位 | 早期城市口径不稳定，容易制造伪精确 |
| 国有资本总额/国企资产 | 暂不进核心 | 与可投资财政点数并非同一口径，收集成本高 |
| 土地价格、水电容量精确值 | 合并为基础设施承载 | 跨年、跨园区可比性弱 |
| 企业数量、上下游数量 | 合并为产业基础 | 企业名录口径变化大，MVP 不值得单列 |
| 专利数量 | 仅作旁证 | 数量不能直接代表技术成熟或量产能力 |
| 工资、人口、人均 GDP | 移出每轮结算 | 对这六类投资决策的边际解释有限 |
| 精确行业利润率 | 可得时展示，否则缺失 | 早期细分行业连续数据不足 |
| 2007—2016 全国工业产能利用率 | 不直接使用官方连续序列 | 国家统计局自 2017 年四季度起才正式发布该序列；早期只能采用产业专门资料或“产量/设计产能”推算 |
| “产业贡献”“项目风险” | 不作为输入字段 | 它们是模型输出，不能与原始数据混为一谈 |
| 成功概率 | 禁止作为状态变量 | 外部事件和玩家决策必须先改变经济变量，再由规则结算结果 |

## 5. 财政点数与多企业组合

### 5.1 点数口径

当前已取得的宏观财政收入、支出、政府性基金、债务和部分项目级政府资本承诺。它们足以约束财政环境、项目资金压力和承诺资本，但仍不足以还原每个阶段全市可自由支配的产业投资余额：缺口包括财政结余、国资平台现金流、产业基金可用余额、项目实缴/提款流水和未披露项目承诺。财政点数因此仍明确作为游戏参数 `scenario_assumption`，不再由宏观财政规模公式生成；真实项目承诺通过 `capacity_evidence` 进入证据层。上一阶段没有使用的余额完整结转；后续补齐现金流与实缴数据后，可通过稳定的 replacement key 替换每阶段新增额度，而无需改动状态机。

```text
new_fiscal_capacity = scenario_assumption(stage_id)

gross_resources
= opening_balance
+ new_fiscal_capacity
+ exits_and_returns

available_points
= gross_resources
- committed_capital
- maintenance_cost

carry_out = available_points - 本轮投入
```

每个阶段的假设必须输出 `assumption_id`、`value_type`、`data_attempt_status`、`calibration_status`、`fallback_reason`、`missing_fields`、`attempted_source_ids` 和 `replacement_key`。`source_ids` 必须为空，避免把尝试过的宏观来源误写成点数的校准来源。真实财政数据仅进入财政 Agent 的环境研判和证据面板。

每个项目有三类成本：

- 首投：获得项目席位并启动建设；
- 配套：土地、能源、人才和供应链支持；
- 追加：项目建设或行业低谷中的后续资本。

玩家每轮面对 2—3 家入局企业；它们共享同一财政池，并全部持续演化。MVP 一局不在中途替换这 2—3 家，避免把企业竞争与阶段推进混在一起。不同开局组合可以从六个原型中生成不同局面。

### 5.2 决策动作

MVP 只保留五个动作：

```json
{
  "company_id": "company_a",
  "action": "invest | support | follow_on | restructure | exit",
  "capital_points": 40,
  "support_focus": "infrastructure | talent | supply_chain | financing"
}
```

“税收优惠比例、持股比例、土地面积”等精细控制暂时不开放为自由输入，而是由动作模板映射到规则参数。这样能够避免参数爆炸，同时保留政策含义。

### 5.3 决策反馈

每个动作至少产生三类反馈：

1. 企业直接反馈：现金缓冲、建设进度、技术研发或产能爬坡；
2. 城市间接反馈：财政占用、就业、产业基础、人才与基础设施；
3. 未来反馈：下一轮某些企业获得协同加成，或因财政锁定而无法投入。

示例：对大型显示制造项目投入并补齐基础设施，不应直接得到“成功 +20”，而应先提高建设进度与客户协同；当后续市场价格下行时，企业财务仍会承压，但合肥家电基础可以提高本地产能消化与供应链形成速度。

## 6. Agent 架构与确定性结算

### 6.1 10 小时版只保留四个专业 Agent

| Agent | 输入重点 | 结构化输出 |
|---|---|---|
| 财政 Agent | 财政余量、已承诺资本、项目成本、退出条件 | `affordability`、追加上限、财政风险、理由 |
| 产业 Agent | 本地基础、供应链、人才、基础设施、政策窗口 | `local_fit`、协同项、缺口、理由 |
| 企业技术 Agent | 财务、执行、技术、客户、建设计划 | `execution_outlook`、里程碑、主要失败机制、理由 |
| 市场风险 Agent | 周期、价格、供给压力、宏观事件 | `market_outlook`、冲击方向、敏感项、理由 |

Judge 不再充当第五个“凭感觉打分”的 LLM。编排器收集四个 Agent 的结构化输出，再交给确定性规则引擎结算。

### 6.2 LLM 与规则的边界

LLM 可以：

- 从截止日前证据中提取矛盾与条件；
- 判断风险机制和方向；
- 输出带证据 ID 的结构化理由；
- 在缺失数据下说明不确定性。
- 作为企业 Agent，在给定动作集合内选择扩建、研发、融资、收缩、迁移或等待。

LLM 不可以：

- 直接修改财政点数、企业现金或城市产业基础；
- 直接给出“成功率 +20”；
- 使用 withheld 的未来结果；
- 随口生成产能、营收、税收等数值。

规则引擎负责：

```text
Next State
= Current State
+ Player Action Effects
+ Historical Event Effects
+ Agent Directional Modifiers
+ Path-dependence Effects
```

每项更新都输出 `reason_code`、`input_metric_ids` 和 `delta`，前端才能解释“为什么变”。

### 6.3 最小 Agent 输出契约

```json
{
  "agent": "industry",
  "company_id": "company_a",
  "direction": "positive | neutral | negative",
  "score": 68,
  "confidence": 0.74,
  "key_factors": [
    {"metric_id": "industrial_base", "effect": "positive"},
    {"metric_id": "supply_pressure", "effect": "negative"}
  ],
  "evidence_ids": ["HF-2008-IND-01", "LCD-2008-PRICE-02"],
  "reasoning_summary": "本地客户基础可以降低落地风险，但全球需求下行会延长回报周期。"
}
```

### 6.4 企业自由生长输出契约

每家入局企业每轮都必须输出动作，即使政府没有给钱：

```json
{
  "company_id": "company_a",
  "action": "expand | research | finance | seek_orders | contract | relocate | wait",
  "capital_request_next_round": 35,
  "resource_allocation": {
    "construction": 0.45,
    "research": 0.30,
    "market": 0.10,
    "cash_buffer": 0.15
  },
  "milestone_target": "pilot_production",
  "risk_response": "delay_expansion",
  "evidence_ids": ["CASE-A-PRE-01", "LCD-2008-PRICE-02"],
  "confidence": 0.72
}
```

动作决定“企业想做什么”，规则引擎决定“它实际上做成多少”。这条边界保证企业能够自由生长，又保证数值可以复核。

## 7. 真实数据与反证设计

### 7.1 每条数据的最小元数据

```json
{
  "metric_id": "company_a.financial_health",
  "as_of": "2008-09-30",
  "value": 42,
  "raw_value": {"cash": 0, "debt_ratio": 0},
  "value_type": "observed | derived | ordinal | missing",
  "source_id": "CNINFO-BOE-2008",
  "publication_date": "2009-04-21",
  "available_at_cutoff": false,
  "quality": "A | B | C | D",
  "derivation": "公式或分档规则",
  "confidence": 0.0
}
```

注意：2008 年年度报告在 2009 年披露，不能自动进入 2008 年 9 月的玩家 Context。必须使用当时已经公开的季报、公告或更早资料；年报只能用于更晚截止日或后台结果验证。

### 7.2 数据来源优先级

1. 合肥统计年鉴、统计公报、预算执行报告、政府与部委正式文件；
2. 巨潮资讯的上市公司年报、季报与公告；
3. 国家统计局及国家数据；
4. 行业协会、研究机构、权威数据库；
5. 高质量媒体仅补项目时间线与定性事实，并明确质量等级。

### 7.3 反证不是“复现所有真实数字”

MVP 的 Historical Replay 只验证四件事：

| 检验 | 目标 | 评分方式 |
|---|---|---|
| 方向一致性 | 关键企业/项目指标的上升、下降、停滞方向是否一致 | 命中率 |
| 里程碑时序 | 建设、量产、追加、停滞等先后是否合理 | 顺序匹配 |
| 风险机制 | 是否识别后来真正主导结果的机制 | 标签集合匹配 |
| 路径反馈 | 早期项目是否改变后续财政和产业基础 | 预定义状态断言 |

禁止把真实历史决策本身当成唯一正确答案。历史一致性用于校验模型有没有基本辨识力，反事实方案用于比较机制是否稳定。

### 7.4 六个原型的 MVP 运行与校准要求

六个原型都必须可运行，不再设置“静态 Case 卡”或只按成功/失败区分的占位逻辑。为了在 10 小时内完成，收敛的是每个原型的数据深度和校准目标，而不是可运行数量。

每个原型最少准备：

- 1 个决策截止日和截止日前背景包；
- 10—15 个核心状态字段；
- 1 个初始资金请求与 2—3 个后续资金阈值；
- 3—5 个事件敏感规则；
- 3—4 个真实里程碑或失败节点；
- 1 条历史政府关键决策序列；
- 1 组 Historical Replay 方向、时序和机制目标。

10 小时版重点深测大型显示制造和光伏/重型装备两个原型，但其余四个也必须走同一引擎、能接受任意财政分配并产生后续状态。重点深测代表证据与参数更完整，不代表另外四个仅仅展示。

## 8. 前端最小体验

### 8.1 四屏足够

1. 开场页：一句话任务、2007 初始合肥 State、从六个原型生成本局 2—3 家企业；
2. 决策页：左侧展示期初结余、新增财力、承诺和维护成本，中央展示 2—3 张企业卡及各自资金请求，右侧按本轮实际可用余额分配与操作；

## 11. 验收标准

10 小时结束时，只有同时满足以下条件才算完成：

1. 玩家可以独立完成 S1—S4，不需要开发者手改 JSON；
2. 每轮可在最多 3 家企业间分配总计不超过本轮 `available_points` 的财政点数；未使用部分完整进入下一阶段 `opening_balance`；
3. 每项状态变化都能追溯到玩家动作、历史事件或 Agent 判断；
4. 六个企业原型都能进入推演、接受不同财政分配并继续生长；
5. 六个原型都通过信息截止与 withheld 隔离，其中至少一个历史成功案例和一个历史失败案例完成深校准；
6. 输入真实合肥关键决策序列时，对应企业的方向和核心里程碑在容差内复现；改变关键决策后，历史成功企业可以失败，历史失败企业也可能改善；
7. 同一 seed 与同一输入重复运行，财政与状态数值完全一致；
8. LLM 超时或断网时，fallback 仍能走完整演示；
9. 终局页明确区分“真实观察”“派生指标”“Agent 判断”“模拟结果”；
10. 不宣称随机场景已经获得历史验证；
11. 评委能在终局看到：为何投、发生了什么、为何发生、与真实历史哪里一致或不一致。

---

## 12. 砍功能顺序

若时间不足，按以下顺序砍：

1. 先砍自由文本决策与复杂动画；
2. 再砍非核心事件和每个企业的次要指标，但不砍任何原型的可运行能力；
3. 再砍真实 LLM 在线调用，保留缓存与确定性企业动作 fallback；
4. 再把 S1—S4 压缩为三阶段；
5. 不能砍：六原型统一运行、至少两企业竞争、财政约束、企业持续生长、状态反哺、信息截止、真实决策校准、因果解释。

## 13. 5 分钟演示叙事

```text
0:00—0:30  为什么学合肥：不是背答案，而是在当时的信息条件下做选择
0:30—1:20  从六个原型生成本局三家匿名企业，它们同时竞争由期初结余与新增财力构成的滚动财政池
1:20—2:10  玩家组合投资，专业 Agent 展示冲突判断，三家企业分别决定下一步
2:10—3:00  外部事件到来，已投与未投企业都继续变化，城市资产共同变化
3:00—3:50  下一阶段看到路径依赖：早期产业底座帮助新项目，但财政也被锁定
3:50—4:30  终局揭示真实原型，与历史轨迹进行盲测对照
4:30—5:00  核心结论：系统不是给出唯一答案，而是证明推演受真实数据、时点和可复核规则约束
```

最终对外表达建议固定为：

> 我们把合肥过去十年的产业投资史变成了一个可反证的 Agent 沙盘：六类真实企业可以任意组成一局，在同一历史 Context 下竞争有限财政并持续生长；当玩家复现当年的关键决策时，引擎应复现相应历史方向，改变决策则会长出另一条未来。
