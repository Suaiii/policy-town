# 前后端接口对接说明

> 版本：v0.1
>
> 用途：前端《左右面板信息架构与播报规范 v0.1》与后端契约 `contracts/investment_simulation_v0_1.py` 的对接契约。
>
> 核心结论：**后端结构化输出已覆盖前端设计约 90%，缺的不是「再造数据」，而是一个把后端分散结构统一成前端 `BroadcastEvent` 的适配层，外加补 3 个事件源。**

---

## 1. 四块面板 ↔ 后端结构

| 前端区域 | 后端已有结构 | 对接状态 |
|---|---|---|
| 底部资源条（财政/承诺/城市四指标） | `BudgetState` + `CityMetrics` | ✅ 直接对应 |
| 中央地图（城市/地块/企业状态） | `CompanyState`（status/construction_progress/production_ramp/financial_health/supply_pressure）+ `StateDelta` | ✅ 直接对应 |
| 右侧决策工作台（P02—P09） | `StageResult`（deliberations / state_deltas / belief_updates / commitment_updates / commitment_follow_ups / timeline_events） | ✅ 几乎全对应 |
| 左侧播报流（11 种 BroadcastEvent） | 分散在 6 种结构里 | ⚠️ 数据在，结构不统一，需适配 |

---

## 2. 右侧决策工作台 P02—P09 逐段对接

| 前端步骤 | 后端结构 | 状态 |
|---|---|---|
| P02 阶段入场 / 城市现状 / 资源约束 | `BudgetState`（assumption、carry_out、committed_capital）+ `CityMetrics` | ✅ |
| P03 企业全景 / 单企业申请 | `CompanyState`（capital_request、capital_intensity、financial_health、execution_ability…） | ✅ |
| P04 联席摘要 / 四部门 / 质询 / 核验问题 | `JointMeetingSummary` + `DepartmentMemo` + `DepartmentChallenge` + `VerificationQuestionCard` | ✅ |
| P05 企业回应 / 条件单 / 反提案 / 确认 | `EnterpriseDisclosure` + `GovernmentConditionSheet` + `EnterpriseCounteroffer` + `EnterpriseResponse` | ✅ |
| P06 企业意图 / 一图两账 | `CompanyAction` + `BeliefLedgerEntry` + `CommitmentLedgerEntry` | ✅ |
| P07 结算 | `StateDelta` + `StageResult` | ✅ |
| P08 变化因果链 / 承诺账 / 收束 | `StateDelta`（reason_code/input_metric_ids/evidence_ids）+ `CommitmentFollowUp` + `TimelineEvent` | ✅ |
| P09 终局解密 / 双时间线 / 命题复盘 / 双组评价 | `FinalResult`（story_timeline）+ `ReplayScores`（decision_baselines + prediction）+ `OutcomeForecast` | ✅ |

**右侧这块后端契约和前端设计基本一一对应，前端只需读 `StageResult` 按步骤切片展示，几乎不用后端改。**

## 3. 左侧播报流：11 种 BroadcastEvent 对接（含缺口）

| 前端 11 种播报 | 后端现状 | 缺口 |
|---|---|---|
| `media`（媒体） | ❌ 无媒体实体 | **后端无此数据源**，需降级或补媒体数据 |
| `natural_event`（自然事件） | `HistoricalEvent`（external_shock 类） | 需映射 |
| `policy`（政策） | `policy_library`（在 `real_data_context.policies`） | 需映射 |
| `city_update`（城市变化） | `StateDelta`（entity=city） | ✅ |
| `enterprise_action`（企业动态） | `CompanyAction` + `TimelineEvent`（enterprise_response） | ✅ |
| `department_interaction`（部门） | `DepartmentChallenge` + `DepartmentMemo` | ✅ |
| `government_enterprise`（政企交互） | `NegotiationEvent`（6 个 phase） | ✅ |
| `player_decision`（用户决策） | ❌ 无显式事件 | 需从 `PlayerAction` + `NegotiationChoice` 派生 |
| `settlement`（结算） | `StateDelta` + 结算状态 | 缺显式「结算成功/失败」事件 |
| `commitment`（承诺） | `CommitmentFollowUp` + `CommitmentLedgerEntry` | ✅ |
| `audit`（证据/过滤/降级） | `EvidenceFilterDecision` + `FrozenContextAudit` | ✅ |

**结论：缺 3 个事件源（media / player_decision / settlement），其余 8 种后端数据已存在，只差统一出口。**

## 4. BroadcastEvent 契约（后端模型）

后端新增 `BroadcastEvent` 模型，字段与前端 TS Schema 一一对应（见前端规范第 7 节）：

```text
event_id / run_id / stage_code / related_step
logical_time / observed_at / available_at / cutoff_date
visibility（player_visible | audit_only | sealed）
type（11 种）/ priority（normal | important | critical）/ status（new | read | acknowledged | expired）
actor_id / actor_type（media | city | department | enterprise | player | system）
target_id / affected_entity_ids
title / summary / impact_tags / thumbnail_url
evidence_ids / reason_codes / related_decision_id / related_snapshot_id
requires_acknowledgement / pin_until（acknowledged | stage_end | resolved）
navigation_target（surface：map | right_panel | evidence_drawer | commitment_ledger + target_id）
```

## 5. phase ↔ step ↔ 唯一主操作映射表

后端 `NegotiationEvent.phase`（6 个）↔ 前端右侧步骤：

| 后端 `NegotiationEvent.phase` | 前端步骤 | 唯一主操作 |
|---|---|---|
| `verification_question` | P04 核验问题 / P05 核验概览 | 向企业发起核验 |
| `enterprise_disclosure` | P05 企业回应 | 制定政府条件 |
| `government_condition` | P05 政府条件单 | 提交政府条件单 |
| `enterprise_counteroffer` | P05 企业反提案 | 确认处理方式（接受/改一次/放弃） |
| `final_commitment` | P05 最终条件确认 | 确认政府决策 |
| `rule_settlement` | P07 结算成功/失败 | 查看阶段变化 / 重试 |

部门侧（`DepartmentMemo` / `DepartmentChallenge`）不产生独立的 phase，直接落在 P04 的联席摘要 / 四部门立场 / 质询三个子视图。

## 6. 适配器职责与接入点

新增 `policytown/investment/broadcast.py`，输入 `StageResult` + `StageInput`，输出 `list[BroadcastEvent]`：

```text
StageResult（分散结构）
    ↓
broadcast.build_broadcast_events(stage_result, stage_input)
    ↓
list[BroadcastEvent]（11 种 type，按 sequence 排序）
```

映射来源：

| BroadcastEvent type | 来源结构 | priority 规则 |
|---|---|---|
| `audit` | `frozen_context_audit.decisions`（withheld 项） | 泄漏/拒绝未来证据 = critical |
| `policy` | `real_data_context.policies` | normal |
| `natural_event` | `events`（HistoricalEvent） | magnitude 高 = critical |
| `department_interaction` | `department_memos` + `meeting.challenges` | 立场变化 = important |
| `government_enterprise` | `negotiation_log`（6 phase） | 拒答 = important |
| `player_decision` | `StageInput.actions` + `negotiations` | normal |
| `enterprise_action` | `company_actions` | normal |
| `settlement` | 结算成功/失败显式事件 | 失败 = critical |
| `city_update` | `state_deltas`（entity=city） | normal |
| `commitment` | `commitment_follow_ups` + `commitment_updates` | 违约/暂停 = critical |
| `media` | ❌ 暂无 | 见第 7 节 |

接入点：`run_stage` 返回前调用适配器，把结果挂到 `StageResult.broadcast_events`。

## 7. 三个缺失事件源的解决方案

1. **`player_decision`**：从 `StageInput.actions`（`PlayerAction`）+ `negotiations`（`NegotiationChoice`）派生一条「决策已记录」事件，`actor_type=player`，`navigation_target=right_panel`。零新增数据，纯派生。

2. **`settlement`**：在 `run_stage` 结算成功处显式追加一条 `settlement`（`actor_type=system`），失败/异常时追加 `critical` 的 `settlement` 事件并带 `reason_codes`。结算本身就是规则引擎的确定性动作，加一条显式事件即可。

3. **`media`**：当前数据线没有抓媒体新闻，两个选项——
   - **降级（推荐，MVP 先做）**：不生成 `media` 事件，媒体相关信息并入 `policy` / `natural_event` / `city_update`，前端 `media` 形态留空；
   - **补数据**：后续抓真实媒体新闻（标题/时间/行业/影响标签），再独立生成 `media` 事件。此项不阻塞闭环。

---

## 8. 前端消费约定

- 左侧播报流只消费 `StageResult.broadcast_events`，不自己从 6 种结构拼事件；
- 右侧工作台只消费 `StageResult` 的对应字段（第 2 节表），不消费 `broadcast_events`；
- 中央地图消费 `companies`（当前状态）+ `state_deltas`（变化动画）；
- 底部资源条消费 `budget` + `city_metrics`；
- 前端不计算任何数值、不生成事件，全部来自后端结构化输出。
