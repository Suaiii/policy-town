# 最终场景：产品数据闭环

> 场景锁定：头部企业因 AI 与组织重构，在两个季度内调整约 5000 个岗位；市人社局在 2 亿元预算、六类政策工具和一个季度考核周期内制定应对方案。
>
> 产品落点不是预测真实裁员人数，而是检查一套政策工具组合的预算、启动时序和资格条件：谁等得到、谁被遗漏、行为如何绕开、代价落在谁身上，以及考核指标是否掩盖了真实损失。

## 一、把现实数据收束成五层

产品只保留一条数据主线：

```text
现实来源
  → 可核验事实
  → 场景约束与模型假设
  → 同条件方案对照
  → 体检卡、统计盲区与七问报告
```

| 数据层 | 存什么 | 能做什么 | 不能做什么 |
|---|---|---|---|
| S1 现实来源 | 政策原文、统计公报、企业披露、论文、招聘数据 | 提供出处 | 直接驱动人物行为 |
| S2 可核验事实 | 资格线、补贴标准、制度流程、已披露事件 | 形成硬规则或背景事实 | 自动外推本市比例 |
| S3 模型假设 | 5000 人、2 亿元、储蓄分布、转岗成功率、企业反应概率 | 构造可运行城市 | 冒充现实统计 |
| S4 推演事件 | 分批、转岗、停招、培训、退出等事件流 | 生成画面和指标 | 作为现实预测 |
| S5 派生结论 | 等不到救援、对象错配、替代效应、统计失真 | 比较方案并形成建议 | 宣称因果已被现实证明 |

界面统一标识：

- `现实规则`：有可追溯的政策或统计来源；
- `场景设定`：为了推演而输入的城市与事件参数；
- `模拟结果`：当前规则、随机种子和主体样本下的输出。

任何数值从来源进入报告，都必须保留 `source_id → constraint_id → event_id/metric_id → finding_id` 的追溯链。

## 二、现实数据如何进入产品

### 2.1 来源登记

每条现实数据先登记，不直接写进 Agent prompt：

```yaml
source_id: cn_hrss_2026_39
source_type: policy
title: 人社部发〔2026〕39号
publisher: 人力资源社会保障部等
published_at: 2026-06-18
geography: 全国
url: https://policy.mofcom.gov.cn/claw/clawContent.shtml?id=106257
verification: verified
supports:
  - 稳岗返还资格与比例
  - 一次性扩岗补助对象与标准
  - 证岗相适
limitations:
  - 地方执行标准可能另有细化
```

来源分为四种：

| 来源 | 产品用途 | 默认等级 |
|---|---|---|
| 政策原文、政府公开数据 | 硬规则、城市基线 | L1 |
| 企业年报或正式披露 | 机制存在、事件背景 | L1 |
| 学术实证研究 | 行为方向、参数范围依据 | L1/L2 |
| 新闻、平台传闻、二手汇总 | 待核线索或场景素材 | 未核验，不进入硬参数 |

### 2.2 事实转约束

现实来源经过审核后，仅能转成以下四类约束：

```yaml
constraint_id: expansion_subsidy_age_rule
source_id: cn_hrss_2026_39
role: hard_rule
field: policy.tools.absorption_subsidy.eligibility.age
value:
  min: 16
  max: 24
confidence: L1
claim_limit: 仅说明国家政策覆盖条件，不代表本场景采用同一地方细则
```

`role` 固定为：

- `hard_rule`：政策资格、计算方式、法定程序；
- `calibration`：为模型参数提供合理范围；
- `mechanism_support`：仅仅证明某种行为机制存在；
- `background`：增强场景真实性，不参与计算。

## 三、产品入口：从“数字”升级为“应对方案”

用户在周一上午进入产品后，看到的不是空白沙盘，而是已载入的危机简报：

```yaml
trigger_event:
  type: mass_job_adjustment
  announced_jobs: 5000
  cause: ai_and_organizational_restructuring
  affected_roles: [运营, 测试, 客服支持]
  horizon_months: 6
  public_attention: high
  data_status: scenario_assumption

decision_context:
  budget_yuan: 200000000
  assessment_horizon_months: 3
  simulation_horizon_months: 12
  decision_owner: 市人社局就业促进处
```

用户调整三类参数：

1. 预算：每个工具分多少钱、覆盖多少人；
2. 时序：第几周或第几月启动、持续多久；
3. 资格：年龄、参保月数、证岗匹配及分档规则。

六类工具使用统一结构：

```yaml
tool_id: skill_conversion_training
enabled: true
start_month: 6
duration_months: 3
unit_cost_yuan: 8000
capacity: 5000
budget_yuan: 40000000
eligibility:
  max_age: 45
  insurance_months_min: 12
  skill_types: [traditional]
measurement_basis: completed_training
source_ids: []
data_status: scenario_assumption
```

六个工具分别为：

```text
enterprise_consultation   约谈企业
stability_refund          稳岗返还/补贴
job_matching              招聘会与承接对接
absorption_subsidy        吸纳补贴
skill_conversion_training 技能转换培训
income_support            失业保险与生活兜底
```

## 四、四套方案是同一实验的四个参数包

四套方案必须共用企业样本、劳动者群体、外部环境、随机种子和 12 个月时长，仅仅改变政策包：

| 方案 | 改变的参数 | 要回答的问题 |
|---|---|---|
| `base` 不干预 | 所有工具关闭，仅保留法定兜底 | 没有增量干预时怎样演化 |
| `draft` 应急方案 | 约谈+稳岗优先；培训第6月；资格严格 | 季度指标好看是否透支长期就业 |
| `fix1` 前置生活保障 | 在 `draft` 上让生活补贴与等待期同步 | 人能否撑到培训与转岗 |
| `fix2` 放开资格线 | 在 `draft` 上删除连续参保要求、年龄分档 | 被制度资格遗漏的人是否减少 |

所有方案保存：

```yaml
experiment:
  scenario_id: draft
  seed: 20260812
  population_profile_version: city_v1
  firm_profile_version: firms_v1
  economic_environment_version: ai_shock_v1
  evidence_bundle_version: evidence_v1
  policy_package_version: draft_v1
```

因此报告比较的是政策包之间的模型内差异，不把组合方案包装成单变量因果实验。

## 五、主体数据只保留会改变结局的字段

### 5.1 企业

| 企业 | 必需状态 | 关键决策 | 对应画面 |
|---|---|---|---|
| A 裁员方 | 调整计划、批次、内部转岗容量、约谈压力 | 延后、分批、转岗、外包、正式裁员 | 批次与流出 |
| B 承接方 | 招聘计划、政策信任、未来解雇成本预期 | 扩招或停招 | 灯牌熄灭 |
| C 换人方 | AI岗位、传统岗位、技能门槛 | 招人、换人、拒绝错配者 | 一进一出/门口受阻 |
| D 服务商 | 外包容量、培训容量、待遇折损 | 承接外包与培训 | 人流转暗 |

### 5.2 劳动者群体

10 个代表 Agent 负责解释选择，宏观 cohort 负责人数对账。每个 cohort 至少保存：

```yaml
cohort_id: a_ops_46_low_buffer_ineligible
label: A厂·运营岗·46岁·存款2个月·不符合资格
count: 620
origin_firm: A
skill_type: traditional
savings_months: 2
age_band: 45_plus
insurance_months: 8
has_matching_certificate: false
subsidy_eligible: false
```

核心状态机：

```text
在岗 → 收到调整通知 → 内部转岗/求职/培训等待/外包/失业
     → 再就业 / 继续失业 / 退出劳动力市场
```

每月结算一次剩余缓冲：

```text
remaining_buffer = savings_months + income_support_months - months_without_adequate_income
```

当 `remaining_buffer <= 0` 且仍未进入可维持生活的就业或保障状态时，才允许进入 `exited`。退出是模型规则，不由 LLM 自由决定人数。

## 六、Agent 与规则引擎的边界

Agent 只负责解释和选择；规则引擎负责人数、预算、资格、时间和指标。

| 模块 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|
| Evidence Agent | 来源登记 | 可用约束与限制 | 编造来源或补齐缺失数字 |
| 政策解析 Agent | 危机简报、工具箱、部门目标 | 结构化政策包 | 直接计算就业结果 |
| 政府四部门 Agent | 当前快照、KPI、预算 | 提案与妥协记录 | 超出工具箱发明权限 |
| 企业 Agent | 政策包、市场状态、企业状态 | 动作意向与理由 | 直接改城市总人数 |
| 劳动者 Agent | 个人约束、可选路径 | 选择与犹豫 | 决定 cohort 总量 |
| 规则引擎 | 全部结构化动作 | 事件流、资金流、状态流 | 输出无法对账的数据 |
| 审计/报告 Agent | 指标、事件、证据链 | 体检卡与七问报告 | 把模拟结果写成现实预测 |

## 七、单月数据流水线

现有八轮可解释为 12 个月内的八个关键结算点；数据顺序固定：

```text
1. 外部环境更新：舆情、AI冲击、岗位需求
2. 政府提案与联席会议：形成工具组合
3. 预算与资格预校验：超预算或规则冲突立即提示
4. 企业决策：A放人、B接人、C换人、D承接
5. 劳动者决策：依据技能、资格和储蓄选择路径
6. 市场结算：岗位匹配、替代、外包和培训排队
7. 生活缓冲结算：扣减等待时间，处理退出
8. 指标结算：官方指标、扩展指标、部门KPI
9. 检测器运行：形成发现与建议
10. Snapshot 落盘：供前端回放与报告复核
```

每个关键行为保存为事件：

```yaml
event_id: evt_draft_m4_cohort17_exit
scenario_id: draft
month: 4
actor_id: a_ops_46_low_buffer_ineligible
event_type: exit_labor_force
count: 240
causes:
  - savings_exhausted
  - training_not_started
  - subsidy_ineligible
policy_tool_ids:
  - skill_conversion_training
constraint_ids:
  - training_start_month_6
```

沙盘、指标和报告必须消费同一事件流，不另造演示数字。

## 八、三个 P0 画面的数据来源

### 8.1 双时钟条

上排由 `policy.tools[].start_month` 驱动；下排由 cohort 的 `remaining_buffer` 驱动。

停帧条件：

```text
month == skill_conversion_training.start_month
```

画面同时显示：

- 培训此刻启动；
- 已退出人数；
- 仍在等待人数；
- 因生活补贴而仍能等待的人数；
- `救援可达率 = 启动时仍未退出且符合资格的人数 / 原计划培训对象人数`。

### 8.2 一进一出

数据必须来自同一企业、同一结算期：

```text
C 的受补贴新招人数 > 0
且 C 的原岗位退出人数 > 0
```

替代效应指标：

```text
净增就业 = 期末在岗人数 - 无补贴对照方案期末在岗人数
替代人数 = 受补贴招聘人数 - 可归因于净增岗位的模拟差额
```

报告仅称“本模型中出现替代”，不称现实企业骗补。

### 8.3 走出地图

仅由 `exit_labor_force` 事件触发。退出后：

- 不再进入官方失业率分子；
- 不再进入劳动力人口分母；
- 仍计入扩展指标 `hidden_unemployment`；
- 保留退出原因，支持点击追溯。

## 九、指标收束为两套账

### 9.1 官方可见账

```text
就业人数
登记/调查口径失业率（按场景定义）
季度再就业率
政策资金执行率
培训完成数
补贴覆盖数
```

### 9.2 产品补充账

```text
隐性失业人数
劳动参与退出人数
有效就业人数
低质量外包人数
技能错配缺口
救援可达率
资格遗漏率
等待期保障缺口
未被干预企业招聘收缩量
补贴净增就业率
```

必须同时展示的统计盲区条件：

```text
官方失业率下降
且 总就业或有效就业下降
且 退出劳动力市场人数上升
```

这时生成提示：`指标更好看，但更多人从统计口径中消失。`

## 十、五个检测器形成建议闭环

| 检测器 | 计算条件 | 输出建议 | 修改参数 |
|---|---|---|---|
| 等不到救援 | `savings_months < tool.start_month` 的目标人数占比过高 | 培训同期生活补贴，或提前培训 | 时序+预算 |
| 对象错配 | 需要帮助但因年龄/参保/证书被排除 | 删除硬切线，改分档或人工复核 | 资格 |
| 替代效应 | 补贴招聘高、净增就业低 | 与净增就业挂钩 | 计量口径 |
| 死角损失 | 补贴流向本来就不裁的存量岗位 | 要求裁员计划或风险证明 | 补贴对象 |
| 约谈溢出 | A正式裁员下降，同时B招聘显著下降 | 同步公布承接支持以稳定预期 | 配套动作 |

主检测器“等不到救援”输出结构：

```yaml
finding_id: rescue_arrives_too_late
metric:
  target_population: 3100
  unable_to_wait: 1840
  share: 0.594
causes:
  training_start_month: 6
  dominant_savings_months: [2, 3, 5]
recommendation:
  patch:
    income_support.start_month: 1
    income_support.target: training_waitlist
evidence:
  event_ids: [evt_...]
  constraint_ids: [training_start_month_6]
confidence: L3
limitation: 数量来自场景推演，只支持方案间相对比较
```

## 十一、最终交付不再分裂

产品只生成三类互相链接的交付物：

### 11.1 方案总览

回答：选了哪些工具、用了多少钱、何时启动、覆盖谁。

### 11.2 数字与规则体检卡

每张卡围绕一个可调边界：

```text
培训第6月启动
45岁资格线
连续参保12个月
吸纳补贴0.5万元/人
稳岗补贴0.5万元/人
```

卡片统一回答：

1. 谁会贴着边界行动；
2. 谁被挡在边界外；
3. 代价转嫁给谁；
4. 改动边界后方案差异如何；
5. 来源与可信度到哪一级。

### 11.3 七问报告

七问报告只汇总已经生成的事件、指标和体检卡：

```text
保护了谁
会被怎么用
谁减少招聘
谁被遗漏
哪个指标误导
如何调整
调整后副作用是否下降
```

报告中的每条数字必须可点击回到指标计算，再回到事件和来源；报告 Agent 不得另外创造结论。

## 十二、与当前仓库的落点

| 产品数据 | 当前落点 | 下一步 |
|---|---|---|
| 场景与方案 | `scenarios/manifest.json` | 重命名为 `base/draft/fix1/fix2` 并存完整政策包 |
| 政策工具 | `contracts/schema.py::Policy` | 增加工具列表、预算、启动时间和资格条件 |
| 劳动者约束 | `WorkerAction` | 增加年龄段、参保月数、资格、剩余缓冲 |
| 企业动作 | `FirmAction` | 增加内部转岗、受补贴招聘、岗位退出与政策信任 |
| 事件流 | 目前分散在 firms/workers/flows | 增加统一 `events[]` 与原因链 |
| 指标 | `Metrics` | 增加救援可达率、资格遗漏率、有效就业与补贴额外性 |
| 检测 | `policytown/detectors.py` | 增加五个最终场景检测器 |
| 回放 | `data/run_*/round_*.json` | 新场景另建快照，不覆盖已存在的用户改动 |
| 双时钟画面 | `frontend/src/city/v3/policyFeed.ts` | 从工具启动月与剩余缓冲生成，不写死文案 |
| 报告 | `policytown/reporting.py` | 仅消费检测器、指标、事件和证据引用 |

建议将 `Snapshot` 契约升级到 `1.3`，但保留读取 `1.2` 的兼容层。先完成数据契约和一组 `draft` 快照，再做 UI；否则双时钟、检测器和报告会分别形成三套不一致的数据。

## 十三、P0 开发顺序

```text
P0-1 证据登记与场景参数分层
P0-2 Policy/Worker/Metrics/Events 契约 1.3
P0-3 draft 规则结算：培训时序、储蓄扣减、资格判断、退出
P0-4 rescue_arrives_too_late 检测器
P0-5 双时钟画面
P0-6 fix1 同条件对照
P0-7 统计盲区与七问报告
P1   替代效应、约谈溢出、fix2、其余卡片
```

第一条可验收闭环是：

```text
用户把培训设为第6月
→ 2/3/5月缓冲群体依次耗尽
→ 退出事件进入 Snapshot
→ 培训启动时双时钟停帧
→ 检测器命中“等不到救援”
→ 一键生成“同步生活补贴”的 fix1
→ 同 seed 重跑后，救援可达率提高、隐性失业下降
→ 报告明确这些变化是模型内方案差异
```

做到这一条，现实数据、Agent、规则引擎、沙盘、检测器和报告才真正成为一个产品，而不是几个并排展示的模块。
