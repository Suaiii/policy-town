# 城市产业投资 Agent 推演场：精简产品文档

> 参赛方向：赛题三「政企互动 Agent 推演场（GOVBIZ SIMULATOR）」  
> 当前验证城市：合肥，2007—2016  
> 产品愿景：让每一个城市都能跑出属于自己的“合肥模式”

## 一、目标用户与核心问题

### 1. 产品目标

“合肥模式”不是照搬合肥投过哪些企业，而是一种能力：城市能够结合自身财政条件、产业基础、人才供给、区位资源和发展阶段，识别适合自己的产业机会，并通过政府、企业及相关主体的持续博弈形成可执行的产业路径。

本产品以合肥 2007—2016 年产业投资史作为首个验证场，把真实城市数据、企业项目、政策环境和历史事件装入多 Agent 推演系统。系统的最终目标不是复刻一个标准答案，而是让不同城市输入自己的条件，比较不同招商、投资和扶持组合，在推演中找到符合自身禀赋的产业发展模式。

### 2. 目标用户

- **城市政府与职能部门**：比较产业方向、项目组合、财政投入与政策工具的影响。
- **园区和招商团队**：评估企业与本地产业链、人才、基础设施及区位条件的匹配度。
- **政府投资平台和产业基金**：分析项目能力、资本需求、追加风险、里程碑与退出条件。
- **企业及项目方**：理解政府目标和资源约束，测试不同落地方案及承诺条件。
- **高校、研究机构和公众**：用于产业政策教学、城市发展研究和公共决策体验。

### 3. 核心问题

现实中的产业项目并不是企业提交申请、政府给出审批结论的单线流程。企业诉求、部门目标、园区承载能力、财政约束、市场周期和政策工具彼此交织；支持一个项目也会占用未来资源，并影响其他项目和后续产业机会。

现有分析方式通常只能复盘单个成功案例，难以回答三个问题：

1. 在当时能够获得的信息下，这项决策是否合理？
2. 政府、企业和相关主体的不同目标如何影响最终方案？
3. 如果资源分配或合作条件发生改变，城市会走向怎样的产业路径？

产品通过可追溯的多 Agent 连续推演，将这些相互影响的因素放进同一个城市状态中，帮助用户理解“什么产业适合这座城市，以及怎样的政企协作能够让它真正落地”。

## 二、方案与赛题的对应关系

赛题要求用 AI 智能体模拟企业、政府部门、园区、投资机构和公众等主体，围绕招商、政策、审批、补贴、产业落地、就业带动与城市发展进行决策、协商、博弈和演化。本产品以“政府产业投资”作为主场景，与赛题形成以下对应：

| 赛题要求 | 产品设计 | 当前实现 |
| --- | --- | --- |
| 模拟不同类型主体 | 财政、经信、科技、发改四类政府 Agent 与企业 Agent 拥有不同目标、信息和约束 | 政府部门与企业 Agent 已进入后端闭环；园区、投资机构和公众作为后续角色扩展 |
| 体现政企互动 | 政府研判项目，企业根据资源和条件作出披露、接受、反提案或经营行动 | 已实现部门研判、企业响应和企业自主行动的基础能力 |
| 围绕招商与产业落地决策 | 多家企业竞争同一财政池，系统同时考虑产业基础、技术、市场、人才、供应链和项目执行 | 已实现匿名企业组合、财政分配和状态结算 |
| 展示协商与博弈 | 部门先独立判断，再围绕真实分歧质询；政府条件与企业诉求形成有限协商 | S1 基础链路已实现，复杂条款暂不作为前端必经操作 |
| 展示城市长期演化 | 每轮结果写回城市、财政和企业状态，成为下一阶段的决策条件 | S1—S4 连续状态演化已跑通 |
| 发挥 AI 的关键作用 | AI 理解多源材料、扮演不同主体、形成判断与行动；规则引擎负责数值结果 | 已形成“Agent 判断 + 规则结算”的混合架构 |

因此，我们不仅仅是在做一个合肥历史模拟器。合肥是系统的首个历史验证样本；产品真正回应赛题的方式，是搭建一个能够迁移到不同城市、容纳多类政企主体并持续演化的 Agent 推演场。

## 三、核心功能与业务流程

### 1. 核心功能

#### 城市 Context 建模

将城市财政、产业基础、人才、供应链、基础设施、政策和市场周期构造成同一个城市状态。所有企业在同一城市、同一阶段和同一资源约束下参与推演，前一轮结果会改变后一轮条件。

#### 历史信息截止与证据追溯

每条材料记录来源、发布时间和可知日期。系统仅允许 Agent 使用决策截止日前已经公开的信息，未来年报、项目结果和事后报道在终局前保持隔离，避免用结局倒推决策。

#### 多主体 Agent 研判

财政、经信、科技、发改分别从财政安全、产业协同、技术可行性和长期规划出发独立判断；企业 Agent 则根据自身能力、资金需求、外部环境和既有承诺作出响应。系统呈现主体之间的共识、分歧、红线和条件，而不是输出一个黑箱答案。

#### 产业项目组合决策

每阶段有 2—3 家匿名企业共同竞争有限财政资源。用户需要比较项目与城市的匹配度，并在企业之间配置财政点数。支持一家企业会减少其他项目和未来阶段的可用资源。

#### 企业行动与城市演化

政府决策提交后，企业可以扩建、研发、融资、争取订单、收缩或等待。规则引擎统一结算财政余额、建设进度、企业状态、产业协同和城市公共价值，并将结果写入下一阶段。

#### 终局历史回放

四阶段结束后，系统揭示匿名企业对应的真实原型，对照用户决策路径、真实历史关键动作和后来结果，解释哪些选择形成了关键分叉，以及哪些判断受到了信息不足的限制。

### 2. 业务流程

```text
创建城市推演
→ 读取当前阶段的城市 Context、政策与财政池
→ 多家匿名企业提交项目与资金诉求
→ 四部门 Agent 独立研判、识别分歧并形成联席摘要
→ 用户比较项目，为企业分配财政资源
→ 企业 Agent 根据政府方案作出响应与经营行动
→ 历史事件和确定性规则引擎统一结算
→ 展示财政、企业、产业和城市状态变化
→ 新状态进入下一阶段并重复推演
→ 终局揭示真实案例，完成历史回放和决策复盘
```

当前前端主流程将用户操作收敛为“调整各企业财政点数 → 确认组合并执行模拟”。部门意见、企业行动、证据、承诺和完整因果链作为可展开信息，不设置为阻塞流程的连续页面。只有当核验问题、风险条款、分期方式和反提案能够产生经过验证的独立结算效果后，才会重新开放为决策操作。

## 四、AI 承担的关键任务、实现方式与链路

### 1. AI 承担的关键任务

- **理解城市与项目材料**：从城市统计、政策、企业年报、项目资料和历史事件中提取当前决策所需的事实与缺口。
- **模拟差异化主体**：让不同部门和企业依据各自目标、指标、红线、私有状态和承诺形成独立判断，而不是共享同一个答案。
- **识别冲突并组织协商**：比较各主体立场，定位真正可能改变决策的争议，形成定向质询、条件方案和保留意见。
- **生成企业行动意向**：企业 Agent 根据获得的资源、项目状态和市场环境决定扩建、研发、融资、争取订单、收缩或等待。
- **解释推演结果**：将证据、Agent 判断和规则产生的状态变化连接成可阅读的因果链，说明为什么发生变化。

AI 不直接编造财政、营收、产能或就业数值，也不替用户作出最终决策。数值变化与资源守恒由规则引擎处理。

### 2. 实现方式

系统采用“数据提供事实，Agent 负责判断，规则引擎负责演化”的混合架构：

```text
真实城市、产业、企业、政策与事件数据
→ Context Builder 按历史截止日过滤并生成事实快照
→ 政府部门 Agent 独立初审
→ 编排器识别分歧，触发有限质询并生成联席摘要
→ 用户提交企业组合与财政分配
→ 企业 Agent 生成响应和下一步行动意向
→ 确定性规则引擎执行财政守恒与 State Transition
→ 保存城市、企业、判断和承诺的新快照
→ 下一阶段继续推演
→ Historical Replay 使用此前隐藏的真实结果完成验证
```

### 3. 关键技术约束

- **时间约束**：通过信息可知日期过滤未来材料，防止 Agent 偷看结局。
- **证据约束**：Agent 的主张、风险和行动理由关联具体证据或明确标注信息缺失。
- **数值约束**：财政及状态变化由确定性规则引擎计算；同一状态、输入和随机种子可以复现。
- **记忆约束**：SQLite 按 `run_id` 保存现实事实、主体判断和双方承诺，避免把全部历史对话直接塞入模型。
- **运行约束**：模型超时、输出格式错误或断网时切换到确定性 fallback，保证现场演示能够完成。
- **前后端边界**：前端仅提交用户决策并展示结构化结果，不在浏览器内另行计算一套模拟结果。

### 2. 现场可演示范围

现场能够演示一条真实的合肥产业投资闭环：

1. 进入 2008 年历史决策时点，查看城市 Context 和有限财政池。
2. 展示未来信息隔离，证明 Agent 看不到后来发布的年报和项目结局。
3. 查看匿名企业申请、四部门立场、分歧和证据。
4. 调整企业财政点数并提交投资组合。
5. 查看企业自主行动、财政守恒及企业和城市指标变化。
6. 通过后端 API、CLI 或 JSON 连续运行 S1—S4。
7. 在终局揭示企业原型，对照用户路径与真实历史，并查看信息泄漏审计。

### 3. 当前边界

- 当前产品验证的是合肥历史场景，尚未完成其他城市的一键数据接入与自动建模。
- 园区、投资机构和公众 Agent 尚未成为独立的可运行角色，目前主要实现政府部门与企业之间的互动。
- 前端仍在接入，部分高级能力需要通过 API、CLI 或 JSON 展示。
- 当前输出用于比较决策方向、机制与路径，不用于预测现实项目的精确收益或成功率。
- 系统模拟的是受约束的多主体决策机制，不宣称复原真实政府会议或证明历史因果。

已完成合肥 2007—2016 年 S1—S4 后端推演闭环，包括真实数据入库、截止日信息过滤、四部门 Agent 研判、企业行动、财政守恒、城市状态演化和历史回放。现场可演示 2008 年盲测：查看匿名项目与部门分歧、分配财政点数、执行结算并追溯证据，也可通过 API/CLI 连续跑完四阶段。当前 Web 前端仍在接入；园区、投资机构和公众 Agent 及其他城市的数据接入属于后续范围。

## 六、创新点及后续延展空间

### 1. 创新点

#### 从复制合肥答案转向生成城市自己的发展路径

产品抽象的是合肥在有限资源下识别产业机会、协调政企目标和持续投入的决策机制，而不是把“投资某几家企业”包装成通用答案。未来每座城市都以自己的财政、产业、人才、区位和政策条件为起点，推演出不同的产业组合与协作条件。

#### 将真实历史变成截止日盲测

多数历史分析站在结局之后解释成败。本产品先冻结当时可知的信息，让 Agent 在不知道结果的情况下判断，终局再用真实历史验证方向、时序、机制和信息纪律，使推演具备可证伪性。

#### 多主体博弈取代单模型建议

系统不询问一个模型“应该投谁”，而是让财政、产业、科技、发展规划和企业主体依据不同目标互动。产品展示的是冲突如何形成、什么证据能够改变立场，以及什么条件可以促成合作。

#### AI 判断与规则结算分离

Agent 擅长理解材料、表达偏好和模拟行动，规则引擎负责预算守恒与状态变化。二者分工减少数值幻觉，也使每次变化都能回到输入、公式和证据。

#### 连续城市状态与路径依赖

多个项目共享同一个城市状态。一次投资既会消耗财政，也可能形成供应链、人才、基础设施和政府信用，进而改变下一次项目落地的条件。产品模拟的不是孤立审批，而是城市产业能力的长期形成过程。

### 2. 后续延展空间

- **城市迁移**：建立标准化城市数据接入模板，将财政、产业、人才、区位、园区、政策和企业项目映射为统一 Context，使不同城市能够创建自己的推演场。
- **主体扩充**：加入园区、产业基金、银行、科研机构、公众和媒体 Agent，覆盖招商、审批、融资、补贴、就业与公共反馈。
- **政策工具扩充**：在完成差异验证后开放土地、人才、基础设施、分期拨付、里程碑、担保、审计、重组和退出工具。
- **真实项目压力测试**：让城市输入候选项目和资源方案，对不同投资组合、政策条件与外部冲击进行多轮比较。
- **城市模式对比**：形成跨城市推演实验，比较相同项目在不同城市禀赋下的落地结果，以及不同城市如何形成各自的产业路径。
- **教学与公众体验**：生成个人决策报告，用于公共管理、产业经济、招商培训和城市发展科普。
- **评测体系完善**：增加重复运行稳定性、反事实敏感性、Agent 校准度、跨模型对比和长期路径评价。

产品的长期形态不是“合肥模式复制器”，而是一套城市产业发展实验基础设施：让每座城市看清自己的条件、约束与机会，并通过多主体 Agent 推演，跑出属于自己的“合肥模式”。
