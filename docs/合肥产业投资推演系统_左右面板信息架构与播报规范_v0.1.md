# 合肥产业投资推演系统：左右面板信息架构与播报规范

> 版本：v0.1  
> 用途：产品、UI/UX、前端、Agent、后端与规则引擎联调  
> 依据：《合肥产业投资推演系统：详细流程与界面数据交互表》v0.1  
> 核心定义：左侧回答“发生了什么”，右侧回答“现在需要做什么”。

---

## 1. 目标与设计结论

驾驶舱的左右两侧不是两块对称的信息面板，而是两套职责、形态和更新节奏完全不同的系统。

| 区域 | 核心问题 | 职责 | 主要形态 | 更新方式 |
| --- | --- | --- | --- | --- |
| 左侧 | 发生了什么？ | 播报历史环境、媒体信息、自然事件、政策、城市状态、企业动态和 Agent 交互 | 竖向消息流中排列的横向信息条 | 事件驱动、准实时追加 |
| 中央 | 决策落到城市会发生什么？ | 显示合肥城市、项目地块、企业席位和状态变化 | 3D 决策桌和合肥地图 | 随选中态和 `StateDelta` 更新 |
| 右侧 | 现在需要做什么？ | 呈现当前任务、决策证据、结构化选项、条件、校验与提交反馈 | 稳定的竖向决策工作台 | 随必经流程切换 |
| 底部 | 资源和城市状态变成什么？ | 长期监控财政、承诺资本、维护压力和城市指标 | 常驻资源条 | 条件预览或结算后刷新 |

最重要的分流规则：

- 只需要用户知道、不需要填写或选择：放左侧播报流。
- 需要用户比较、选择、配置或确认：放右侧决策区。
- 需要观察空间变化：放中央地图。
- 需要长期监控的数值：放底部资源条。
- 需要追溯来源：由当前内容打开证据抽屉。

## 3. 右侧决策工作台

### 3.1 固定信息架构

右侧每一个步骤使用统一的基础结构：

1. 当前任务标题与步骤编号。
2. 当前决策对象，例如全局、企业 A 或某项承诺。
3. 与当前决策直接相关的数据。
4. 当前可见证据、证据质量和数据缺口。
5. 结构化选项、表单或对照内容。
6. 财政、城市资源和承诺影响预览。
7. 字段校验、风险提示和机会成本。
8. 当前屏唯一主操作。
9. 返回、放弃、查看来源等次要操作。

| P02 | 城市现状 | 财政能力、承诺资本、维护成本、产业基础、供应链强度、人才供给、组合公共价值、市场周期、已生效政策 | 切换城市指标；打开数据来源 | 继续 |

### 3.3 右侧禁止内容

以下内容不应进入右侧决策工作台：

- 连续媒体新闻。
- 城市日常播报。
- 与当前任务无关的历史事件。
- 长篇 Agent 对话或逐字生成过程。
- 装饰性“Agent 正在思考”。
- 未经规则引擎确认的预测数值。
- 同时出现两个同等强度的主操作。

## 4. 左侧城市事件与决策播报流

### 4.1 两层结构

#### A. 固定 Context 锚点

左侧顶部保留一块不参与滚动的精简区域，常驻展示：

- 当前历史日期。
- 当前阶段名称。
- 信息截止日。
- 核心矛盾。
- 当前市场周期。
- 最重要风险。
- 未读重要播报数量。

#### B. 动态播报流

Context 锚点下方为动态播报流。整个区域可以竖向滚动，但每条消息必须是宽扁的横向信息条，不使用统一方正卡片。

### 4.2 播报类型

| 播报类型 | 数据内容 | 视觉形式 | 用户可做的事 |
| --- | --- | --- | --- |
| 媒体信息 | 标题、媒体类型、发布时间、涉及行业、影响标签、证据质量 | 小缩略图/媒体图标＋标题＋时间的横向新闻条 | 展开摘要；查看来源 |
| 自然事件 | 暴雨、洪水、高温、供电紧张等；影响区域、严重度、持续阶段和受影响对象 | 全宽警报带；琥珀或红色；不使用普通卡片外框 | 查看影响对象；定位地图 |
| 政策通告 | 政策名称、生效时间、适用行业、可能影响和来源编号 | 公文标签式窄条 | 展开政策摘要；查看证据 |
| 城市播报 | 财政、产业基础、人才、供应链、公共价值和基础设施压力变化 | before → delta → after 的数值变化条 | 定位受影响区域；查看原因 |
| 企业动态 | 提交申请、披露材料、拒答、反提案、扩建意图、融资、收缩、迁移、建设和财务风险 | 企业固定色标＋匿名编号＋动作＋状态 | 定位企业席位/地块；打开相关详情 |
| 政府部门 Agent | 财政、经信、科技、发改的主张、质询、立场变化、共识、分歧和少数意见 | 双方头像/部门简称＋方向箭头＋一句结论 | 定位右侧对应争议；查看证据 |
| 政企交互 | 政府发起核验、企业回应、政府提交条件、企业反提案和承诺形成 | 政府/企业双方标识的对话事件条；只显示摘要 | 定位右侧对应步骤；打开详情 |
| 用户决策记录 | 选择的企业、核验问题、提交的条件、对反提案的处理和最终确认 | “决策已记录”确认条 | 定位本局决策记录 |
| 结算播报 | 结算开始、输入校验、财政守恒、快照生成、结算成功或失败 | 系统状态条；不伪装成媒体新闻 | 打开结算详情；失败时定位右侧重试 |
| 承诺提醒 | 承诺即将到期、已满足、延迟、违约、被豁免或触发下一笔资金 | 可置顶的待处理提醒条 | 打开承诺账；定位对应企业 |
| 证据与审计 | 新证据可见、无截止日前证据、未来材料被过滤、fallback 和 Schema/超时异常 | 灰蓝色系统条 | 打开证据抽屉或错误详情 |

### 4.3 播报更新机制

左侧不是无限生成的“假新闻流”，而是基于结构化系统事件的准实时播报。

1. 后端、Agent、证据系统或规则引擎产生完整结构化事件后，左侧立即追加一条。
2. 不展示逐字生成，不展示“Agent 正在输入”。
3. 没有新事件时保持安静，不为了营造热闹自动制造播报。
4. 结算数值一次性刷新，不逐个跳动。
5. 普通播报新增时进行轻量滑入或高亮，然后按时间顺序下移。
6. 重要警告、待处理承诺和自然灾害可置顶，直到阶段结束或用户确认。
7. 同一轮连续的部门讨论折叠为一个事件组，不将长对话拆成十几条刷屏。
8. 屏幕默认同时显示最近 4—6 条，更早内容进入“全部播报”抽屉。
9. 用户浏览旧消息时，新消息不得强行将滚动位置拉回最新处。
10. 用户可暂停自动滚动，但后台继续记录新事件并更新未读数。
11. 与当前步骤直接相关的播报可点击定位右侧内容，但不在左侧提交决策。
12. 所有播报使用游戏内逻辑时间或历史事件时间，不混用现实设备时钟制造虚假实时感。

### 4.4 播报优先级与生命周期

| 优先级 | 示例 | 展示规则 | 是否需要确认 |
| --- | --- | --- | --- |
| `normal` | 普通媒体摘要、部门主张、企业一般动态 | 新增时高亮；按时间正常下移 | 否 |
| `important` | 关键证据出现、企业拒答、部门立场变化、承诺即将到期 | 延长高亮；可暂时置顶 | 可选 |
| `critical` | 自然灾害、财政守恒失败、承诺违约、结算失败、信息泄漏风险 | 持续置顶；强语义警示；阶段切换前不自动消失 | 是 |

## 5. 不同播报的形态规范

左侧不使用“所有内容都是方正卡片”的表达。形态由信息类型和语义决定。

### 5.1 普通信息条

```text
┌──────────────────────────────┐
│ 经信  →  财政                  刚刚 │
│ 接受分期投入，但要求提高建设约束 │
│ #立场变化  #企业A            查看证据 │
└──────────────────────────────┘
```

### 5.2 媒体新闻条

```text
┌──────────────────────────────┐
│ [缩略图]  制造业信贷环境继续收紧   │
│           财经媒体 · 2008-09-18    │
│           #融资风险  #新型显示   │
└──────────────────────────────┘
```

### 5.3 自然事件警报带

```text
╔════════ 城市预警 ════════════╗
║ 强降雨影响经开区物流与施工窗口   ║
║ 影响：企业B、供应压力、建设周期   ║
╚══════════════════════════════╝
```

### 5.4 城市指标变化条

```text
┌──────────────────────────────┐
│ 供应链强度       52  +4  →  56      │
│ 来源：企业A建设＋上游配套进入   │
└──────────────────────────────┘
```

### 5.5 企业与政府 Agent 交互条

- 财政、经信、科技、发改使用固定色。
- 显示发起方、受众方、交互类型和一句结论。
- 立场变化时显示 `before → after`，不播放冢长对话。
- 无证据时明示“缺失声明”，不自动补造理由。

## 6. 左侧播报交互规则

左侧只提供阅读、追溯和定位，不承担主决策。

允许的操作：

- 展开/收起播报摘要。
- 打开证据抽屉。
- 定位地图上受影响的区域、企业或项目。
- 定位右侧对应的争议、回应、承诺或变化因果链。
- 按全部、媒体、政策、城市、企业、部门、系统筛选。
- 暂停/恢复自动滚动。
- 标记已读或确认重要预警。

禁止的操作：

- 在播报条中直接投资、批准、拒绝或修改条件。
- 通过自由输入绕过右侧有限状态机。
- 点击媒体新闻后直接改变数值。
- 将企业意图当作已结算结果。
- 将装饰性城市效果当作实际数据。

## 7. 播报事件数据 Schema

```ts
type BroadcastEventType =
  | 'media'
  | 'natural_event'
  | 'policy'
  | 'city_update'
  | 'enterprise_action'
  | 'department_interaction'
  | 'government_enterprise'
  | 'player_decision'
  | 'settlement'
  | 'commitment'
  | 'audit'

type BroadcastEvent = {
  event_id: string
  run_id: string
  stage_code: 'S1' | 'S2' | 'S3' | 'S4'
  related_step: string

  // 时间与可见性
  logical_time: string
  observed_at?: string
  available_at: string
  cutoff_date: string
  visibility: 'player_visible' | 'audit_only' | 'sealed'

  // 分类与优先级
  type: BroadcastEventType
  priority: 'normal' | 'important' | 'critical'
  status: 'new' | 'read' | 'acknowledged' | 'expired'

  // 行为主体
  actor_id?: string
  actor_type?: 'media' | 'city' | 'department' | 'enterprise' | 'player' | 'system'
  target_id?: string
  affected_entity_ids: string[]

  // 展示内容
  title: string
  summary: string
  impact_tags: string[]
  thumbnail_url?: string

  // 追溯与定位
  evidence_ids: string[]
  reason_codes?: string[]
  related_decision_id?: string
  related_snapshot_id?: string

  // 前端行为
  requires_acknowledgement: boolean
  pin_until?: 'acknowledged' | 'stage_end' | 'resolved'
  navigation_target?: {
    surface: 'map' | 'right_panel' | 'evidence_drawer' | 'commitment_ledger'
    target_id: string
  }
}
```

### 7.1 数据来源责任

| 事件数据 | 负责产出 | 前端责任 |
| --- | --- | --- |
| 媒体、政策、自然事件 | Context Builder/证据系统 | 按截止日过滤后呈现；不生成新闻事实 |
| 政府部门立场和质询 | 政府部门 Agent＋编排器 | 展示结构化摘要；不自行生成会议台词 |
| 企业回应、反提案和行动意图 | 企业 Agent | 显示类型、理由和风险；不自行推断企业私有状态 |
| 城市指标变化和结算状态 | 确定性规则引擎 | 播放 `StateDelta`；不自行计算或修改数值 |
| 承诺状态 | 承诺账＋规则引擎 | 提醒到期、触发、违约或豁免；链接来源 |
| 证据可见性、fallback 和异常 | 证据系统/运行编排器 | 如实显示过滤、降级和失败状态 |

## 8. 信息截止与防泄漏规则

1. 左侧每条媒体、政策和城市事件都必须具有 `available_at` 和 `cutoff_date`。
2. `available_at > cutoff_date` 的内容不得进入玩家播报流。
3. 玩家模式下，未来材料只能显示“当时不可知”，不显示标题、摘要、结果和具体发布日。
4. 审计模式可显示过滤路径和原因，但运行中仍不向 Agent 注入未来内容。
5. 媒体缩略图、标题和影响标签同样受截止日约束。
6. 场景假设必须标注为演示、情景或规则结果，不得伪装成真实媒体报道。

## 9. 正式政府公告的位置

红头文件或正式政府决策公告应作为“重大决策形成后的正式查看页”，而不是左侧日常播报流的替代品。

推荐链路：

```text
政府决策确认
    ↓
左侧追加“政府决策公告已形成”横向播报
    ↓
用户点击“查看正式公告”
    ↓
打开红头文件/公告 Overlay
```

正式公告只在以下节点生成：

- 最终政府条件确认后。
- 承诺账已成功写入后。
- 阶段结算成功且快照已生成后。

## 10. 动效和无障碍要求

- 新播报使用 180—280ms 的轻量滑入和透明度变化。
- 禁止大幅度抖动、无限闪烁和连续轮播。
- 重要播报使用边框、色彩、图标和文字共同表达，不只依赖颜色。
- `prefers-reduced-motion` 下关闭滑动，使用瞬时替换或很短的淡入。
- 左侧播报流可通过键盘聚焦，展开后的证据和定位操作必须有明确标签。
- 新消息到达不强制抢占当前焦点。
- 关键预警可使用 `aria-live="assertive"`；普通播报使用 `aria-live="polite"`。

## 11. MVP 实施顺序

### P0：双面板骨架

- 左侧 Context 锚点。
- 最近 4—6 条的播报流。
- 政策、城市、企业、部门、系统五种基础播报形态。
- 右侧当前任务和唯一主操作。
- 播报点击后定位地图或右侧。

### P1：Agent 与承诺播报

- 四部门立场、质询和变化播报。
- 企业回应、反提案和行动意图播报。
- 承诺即将到期、履约、延迟和违约提醒。
- 同一交互链路的事件分组和折叠。

### P2：媒体、自然事件与审计

- 媒体信息条和缩略图。
- 自然事件警报带。
- 全部播报历史抽屉。
- 播报与证据抽屉的完整追溯。
- 玩家/审计可见性和过滤原因。

## 12. 验收清单

### 12.1 右侧决策工作台

- 用户 3 秒内能看懂当前需要做什么。
- 每屏只有一个最强主操作。
- 财政与承诺影响在提交前可预览。
- 失败时保留用户已填条件。
- 只显示与当前决策直接相关的数据。
- 不以媒体消息、城市播报或长 Agent 对话挤占决策空间。

### 12.2 左侧播报流

- 每条信息都是横向条形，不是一组高而方正的统一卡片。
- 媒体、自然事件、政策、Agent 交互和城市变化具有可辨识的不同形态。
- 只在真实系统事件产生后更新，不自动制造虚假实时信息。
- 新消息不强制拉动正在阅读历史的用户。
- 重要警告和到期承诺可置顶且不自动消失。
- 左侧不提供投资、拒绝、批准或修改条件等主决策按钮。
- 每条重要信息都能追溯到证据、企业、部门、决策或结算快照。

### 12.3 信息安全

- 玩家模式不泄露截止日后的标题、内容、结果和具体日期。
- 媒体和自然事件都有明确的事实时间、可知时间和证据编号。
- fallback、情景设定和演示数据均明确标记，不伪装成真实历史信息。
