# 合肥产业投资推演系统：前端联调与交互改造说明 v0.2

> 面向：产品、UI/UX、前端、后端与 Agent 联调人员  
> 目标：用尽可能少的用户操作触发尽可能多的后端模拟，并删除不能产生真实、可控差异的交互。  
> 状态：S1 真实闭环已经打通；S2—S4 复用同一协议。

## 1. 结论

旧版不是完整产品，而是前端和后端分别运行两套模拟：前端硬编码企业、部门报告、事件和结算公式，后端虽然拥有真实 Context、Agent 编排与规则引擎，却没有 HTTP 边界，浏览器也没有调用它。

新版把一轮用户操作收敛为一个组合投资决定：**只为三家企业分配财政点数，然后确认一次**。提交以后，部门研判、企业自主行动、历史事件、财政守恒、状态变化、承诺和下一阶段快照都由后端生成。前端不再计算业务结果。

## 2. 原设计错在哪里

| 原设计 | 问题 | 改法 |
| --- | --- | --- |
| P04 选择核验问题 | 当前核验选择没有稳定改变规则结果，只增加点击 | 删除独立步骤；研判结果由后端随结算返回，需要解释时作为只读依据 |
| P05 多字段政府条件单 | 分期、配套、里程碑和退出条款尚未各自连接独立规则 | 第一版只保留财政点数；字段未形成独立差异前不得重新加入 |
| 企业一次回应、一次反提案、用户再修改 | 增加多轮状态，但当前无法证明每个选择产生独立后果 | 删除操作链；企业响应由后端作为投资组合的结果生成 |
| 前端选择投资/支持/追加/重组 | 行动类型与阶段语义重叠，也给用户过多微观控制 | 用户只配置资金；后端结合阶段、企业状态和历史事件推导企业行动 |
| P06 单独查看企业意图 | 意图本来就是结算输入/产物的一部分 | 合并进一次提交后的结果页 |
| P07 再次确认结算输入 | 与政府最终确认重复 | 合并为“确认组合并执行模拟”一个按钮 |
| P08 多个必经解释页 | 因果链和承诺账是解释工具，不应阻挡下一轮 | 结果页先给结论，需要时再展开追溯 |
| 前端本地 `simulation.ts` 计算 | 造成前后端双真相 | 删除运行职责，只消费 API 返回的结构化结果 |
| `MOCK_EVENT_FEED` | 与真实阶段 Context 无关 | 不进入正式链路；正式事件仅使用后端 `events/broadcast_events` |
| `localStorage` 保存完整模拟状态 | 可被篡改，也无法由后端恢复 | 浏览器只保存 `run_id`；状态以服务端快照为准 |

## 3. 新的一轮交互

```mermaid
flowchart LR
    A["阶段 Context 自动加载"] --> B["三家企业组合分配"]
    B --> C["确认组合并执行模拟"]
    C --> D["后端：研判 + 企业行动 + 事件 + 规则结算"]
    D --> E["结果与关键差异"]
    E --> F["进入下一阶段"]
```

用户每轮只有两个有业务意义的动作：

1. 调整三家企业的财政点数，允许某家为 0。
2. 点击一次“确认组合并执行模拟”。

企业卡上的 `0 / 半额 / 申请额` 是同一数值输入的快捷方式，不是新增决策变量。

## 4. 为什么只保留财政点数

保留一个输入必须同时满足四项要求：

1. 后端契约能够接收。
2. 规则引擎有独立分支或公式使用它。
3. 输出中能指出它改变了什么。
4. 相同输入和 seed 可以复现。

当前财政点数满足以上要求：它改变财政余额、建设进度、现金流、累计支持、企业自主行动与后续承诺压力。

### 已删除输入及恢复条件

| 输入 | 当前是否产生可靠独立差异 | 处理 | 何时允许恢复 |
| --- | --- | --- | --- |
| 核验问题选择 | 否；主要改变文本 | 删除 | 不同问题能改变验证状态，并由规则读取 |
| 风险条款勾选 | 否 | 删除 | 每项条款具有明确触发器、履约状态和结算效果 |
| 分期方式 | 否 | 删除 | 分期进入承诺账并影响后续阶段可用财政 |
| 城市支持工具 | 后端有规则，但与资金分配形成额外微操 | 暂不开放 | 能证明它产生不可由资金量替代的城市/企业差异，并完成平衡测试 |
| 企业反提案处理 | 结构存在，但会迫使用户再次配置 | 暂不开放 | 反提案仅在少数高影响情形触发，且接受/拒绝具有明确后果 |
| 政府行动类型 | 有规则，但阶段适用范围不清晰 | 暂不开放 | 后端根据阶段限制候选项，并提供差异审计 |
| 自由问答 | 不可控 | 删除 | 不进入正式结算，只能作为解释辅助 |

前端不得因为“界面显得丰富”重新加入输入。每新增一个输入，PR 必须附两个相同初始状态、仅改变该输入的输出差异样例。

## 5. 前后端责任

### 前端负责

- 创建或恢复 `run_id`。
- 展示后端阶段 Context、企业状态和财政上限。
- 收集三家企业的 `capital_points`。
- 在本地仅计算“当前输入合计”，用于即时防止超额；最终合法性以后端为准。
- 提交后呈现 `budget`、`company_actions`、`state_deltas` 和下一阶段入口。
- 请求失败时保留用户当前分配。

### 后端负责

- 随机分配三家企业并记录 seed。
- 根据截止日构建 Context，执行未来信息隔离。
- 校验企业集合、财政上限、阶段顺序和重复提交。
- 生成部门研判、企业记忆与自主行动。
- 应用历史事件与确定性规则。
- 返回财政守恒结果、状态差异、证据和下一阶段快照。
- 按 `run_id` 持久化；浏览器刷新后可恢复。

## 6. 当前 API

### 创建本局

`POST /api/runs`

```json
{}
```

返回当前阶段视图：

```json
{
  "run_id": "hefei-894a1c81df42",
  "stage_id": "S1",
  "cutoff_at": "2008-09-12",
  "available_budget": 100,
  "city_metrics": {},
  "companies": [],
  "budget_assumption": {}
}
```

### 恢复本局

`GET /api/runs/{run_id}`

服务端返回尚未完成的下一阶段。前端只在 `localStorage` 保存 `run_id`。

### 提交并结算

`POST /api/runs/{run_id}/settle`

```json
{
  "stage_id": "S1",
  "idempotency_key": "浏览器生成的 UUID",
  "allocations": [
    { "company_id": "company_e", "capital_points": 40 },
    { "company_id": "company_c", "capital_points": 15 },
    { "company_id": "company_a", "capital_points": 0 }
  ]
}
```

请求必须包含本阶段全部在场企业，包括投入为 0 的企业。相同幂等键重复提交返回同一结果；同阶段不同键重复提交返回 `409`。

## 7. 前端页面状态

正式链路只需要以下状态：

| 状态 | 唯一主操作 | 说明 |
| --- | --- | --- |
| `no_run` | 开始真实推演 | 创建服务端本局 |
| `stage_ready` | 确认组合并执行模拟 | Context 与三家企业已加载 |
| `settling` | 无 | 保留输入，禁止重复提交 |
| `stage_result` | 进入下一阶段 | 展示企业行动和关键变化 |
| `error` | 重试 | 不清空资金分配 |
| `completed` | 查看终局 | S4 后进入 Replay |

不再为“联席摘要、核验概览、企业回应、条件单、行动总览、结算输入确认”分别建立必经页面。它们若需要展示，应作为当前阶段或结果页的只读抽屉。

## 8. 结果页最低展示要求

首屏只展示：

- 财政 `before → after`。
- 每家企业的自主行动。
- 每家企业最多 3—4 项关键 `before → after`。
- 进入下一阶段按钮。

原因、部门研判、证据、完整 `StateDelta` 和承诺账放入可选详情，不阻塞主流程。

## 10. 联调验收

- 浏览器网络面板能看到 `/api/runs` 和 `/settle` 请求。
- 前端源码不调用本地模拟结算函数。
- 三家企业的资金合计不能超过后端 `available_budget`。
- 投入为 0 的企业仍会产生自主响应。
- 结算结果包含财政守恒、企业行动和状态差异。
- 刷新页面后，能够凭 `run_id` 从服务端恢复到下一阶段。
- 重复点击不会重复扣款。
- 相同状态下改变资金分配，至少一项企业状态或行动结果发生可追溯变化。
- 页面明确标识财政点数是场景假设，不包装成真实亿元。
- 所有解释性控件即使移除，也不影响从 S1 连续运行到 S4。
